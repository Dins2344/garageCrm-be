# GaragePulse Backend — Working Agreement

`garageCrm-be` — the API for a multi-tenant garage/workshop CRM.
Node 20 · Express 5 · PostgreSQL on Neon via Drizzle ORM · zod · TypeScript
(CommonJS output) · Vitest · Winston · JWT. Deploys as a Docker image
(`node:20-alpine`) to EC2.

**This is a standalone repository.** The web (`garageCrm-fe`) and mobile
(`garageCrm-app`) clients live in separate repos and deploy on their own
schedule. Anything shared with them is duplicated by hand — see
*Compatibility* below.

---

## Non-negotiables

Each of these has already caused a production or CI incident.

1. **Every query is garage-scoped.** A query without a `garage` filter leaks
   one tenant's data to another.
2. **Backend changes stay additive.** Users on already-published mobile builds
   cannot be force-upgraded. No renames, no removals of API fields — old
   clients must keep working against the new API.
3. **Only ever loosen validation, and never add a NOT NULL column without a
   default.** The zod schemas in `models/` run on every create and update, so
   a new required field or a tightened regex starts rejecting saves of
   *pre-existing* rows on unrelated edits; a migration adding a NOT NULL
   column with no default fails to apply against existing rows and the
   deploy does not start.
4. **Never hardcode currency, locale, tax labels or date formats.** They
   resolve from the garage's `country` through `utils/locale.ts` and
   `utils/format.ts`.
5. **No emoji in any output** — SMS, email, PDFs, logs, scripts, CI, commit
   messages. One emoji in an SMS switches GSM-7 to UCS-2 and halves the
   segment size.
6. **Install dependencies under Node 20 / npm 10.** A lock file generated by a
   newer npm fails CI's `npm ci`.

## Layering — controller → usecase → model, strictly

```
WRONG   controller → model          (skips the usecase layer)
WRONG   usecase → req/res           (HTTP leaks into business logic)
RIGHT   controller → usecase → model
```

- **Controllers** parse `req`, call one usecase, send the response envelope.
  Never import models, never branch on business conditions.
- **Usecases** hold all business logic, take destructured plain objects, throw
  `HttpError(message, status)`. Never touch `req`/`res`/`next`.
- **Models** re-export their table from `config/schema.ts`, hold the zod
  validation schemas, and own `toApi()` — the serialiser that reproduces the
  JSON shape the clients expect. No business logic.

`app.ts` builds the Express app with no import side effects so tests can
`supertest` it. Only `server.ts` connects the DB and starts cron/SMS/mail.

## Every new endpoint gets Swagger docs

`/api-docs` is the contract the web and mobile repos integrate against, so an
undocumented or stale endpoint is a broken contract, not a missing nicety.

**Annotations live in `config/swaggerDocs.ts`, not in the route files.**
`config/swagger.ts` globs both, but every one of the existing blocks is in the
central file — keep them together.

**Shared shapes go in `config/swagger.ts` under `components.schemas`** and are
referenced with `$ref: '#/components/schemas/Name'`. Do not re-inline a body
shape that already has a schema.

When you add or change a route:

1. Add an `@swagger` block in `config/swaggerDocs.ts` under the matching
   section banner, with `tags`, `summary`, `parameters`, `requestBody` and the
   response codes the handler can actually return.
2. Mark public routes `security: []` — the spec defaults to `BearerAuth`.
   Platform-admin routes use `security: [{ AdminAuth: [] }]`.
3. If you changed a model or a request shape, update its schema in
   `config/swagger.ts` too.
4. Verify:

```bash
npx tsx scripts/checkSwagger.ts
```

That script fails if any route registered in `app.ts` is missing from the spec,
or if a `$ref` points at a schema that does not exist. It caught 17
undocumented endpoints — every feature added in one recent stretch of work —
plus schemas left stale by the country/locale change.

## Platform admin lives in the database

Admin identities are documents in the `admins` collection (`models/Admin.ts`),
not environment variables. They were env vars with hardcoded fallbacks in
`usecases/adminUsecase.ts`, which meant any deployment that did not set them
accepted a password committed to this repository.

- **`Admin` is deliberately not a `User` role.** `User.garage` is required
  because every user belongs to one tenant; a platform admin belongs to none.
  And `Role` in `types/domain.ts` is hand-mirrored into both client repos, so a
  `super_admin` value would ripple into two codebases for an actor neither
  client renders.
- **`SUPER_ADMIN_SECRET` has no fallback.** The old one was
  `JWT_SECRET + '_admin'`, which became the literal string `'undefined_admin'`
  when `JWT_SECRET` was unset. Missing secret now fails the login outright.
- **`verifyAdminToken` re-reads the admin record on every request.** That is
  what makes `isActive: false` revoke a live session instead of waiting out the
  4-hour token. Do not "optimise" it into a signature-only check.
- **There is no endpoint that creates an admin**, by design. Use
  `npx tsx scripts/manageAdmin.ts create <email> "<Name>"` locally, which needs
  shell access to the environment. **In production the image has no `tsx` and
  no `scripts/` source** (`npm ci --omit=dev`, and only `dist/` is copied), so
  there it is
  `docker compose exec backend node dist/scripts/manageAdmin.js create ...`.
  Anything under `scripts/` that has to run in production must therefore work
  as compiled JS — it does, because `tsconfig.json` includes `**/*.ts`.

**Deploying this to an environment that has never had an `admins` collection
means admin login rejects everything until the script is run.** Seed before or
alongside the deploy, not after.

## The mobile update gate can brick the field

`models/AppRelease.ts` holds one document **per platform** telling the mobile app
whether an update exists and whether it is mandatory. `GET /api/meta/app-update`
is public and runs on every cold start and resume of every device.

- **Absence means nothing is blocked.** There is deliberately no seed script and
  no default for `minSupportedVersion` — every non-empty default is a default
  that blocks somebody. A fresh deploy prompts nobody.
- **Every branch that is not a confident "this build is out of date" returns no
  update.** Unknown platform, unparseable version, no document, `enabled` not
  exactly `true` — all 200, both flags false. An unusable version is *no
  opinion*, never "very old": treating it as old would block every runtime that
  cannot report its version, and updating does not fix a broken version read.
- **The comparison lives here, not in the app.** Anything shipped into a binary
  is frozen forever, including its bugs (non-negotiable #2). The app keeps only
  two guards, both of which can *only* unblock: it ignores a required verdict
  naming the version it is already running, and it ignores a response whose
  echoed `receivedVersion` does not match what it sent.
- **`utils/semver.ts` returns `null`, not `0`, for unparseable input.** `0` reads
  as "equal", which is accidentally safe at today's call sites and inverts the
  moment someone writes `cmp >= 0`. And `1.0.10` is newer than `1.0.9` — a
  string compare gets that backwards, and the app ships 1.0.9.
- **The single most valuable line** is the usecase refusing a
  `minSupportedVersion` newer than `latestVersion`. That state blocks 100% of
  users instantly, including anyone already on the newest build.

**Recovery, when a bad policy has blocked the field.** Set `enabled: false` from
the admin console's App Release page, or clear `minSupportedVersion`. Either
reaches devices on their next launch *or resume* — the app forces a re-check on
resume while blocked, so a rollback does not wait for a cold start. If the
console itself is down:

```
UPDATE app_releases SET enabled = false WHERE platform = 'android';
```

**Raise `latestVersion` only after the build is actually live on Play**, and
never raise `minSupportedVersion` above a version the store can supply.

## Multi-tenancy is a security boundary

```typescript
// Right
await Customer.findOne({ _id: id, garage: garageId });

// Wrong — an id alone is not a scope
await Customer.findById(id);
```

`garageId` comes from `req.user.garage._id`, set by `protect`. New tenant-scoped
entities need a `garage` field, a `{ garage: 1, ... }` compound index, and a
test in `tests/tenantIsolation.test.ts`. Only `adminUsecase` is cross-tenant by
design. Use the `tenant-isolation-auditor` agent when adding or changing
usecases.

## The database is Postgres, and the API still speaks Mongo's dialect

The backend moved from MongoDB/Mongoose to PostgreSQL (Neon) on Drizzle in
September 2026. **The API contract did not move.** Both clients read `_id`
on every object, and a published mobile build cannot be forced to upgrade, so:

- **Primary keys are 24-hex ObjectIds in a `text` column**, generated by
  `utils/ids.ts`. The TS property is literally `_id`. Do not introduce
  integer or UUID keys on anything a client sees.
- **`toApi()` in each model is the contract.** A reference column
  `customerId` goes out as `customer` — the id string when not joined, the
  object when it was — exactly as a Mongoose ref did. Populate projections
  are the `columns: {...}` on each `with:`; keep them identical to what the
  endpoint returned before.
- **Embedded arrays are JSONB** (`estimation`, `statusHistory`, `complaints`,
  `photos`, `address`, `settings`, `supplier`). Append to `statusHistory` with
  `historyEntry()` from `models/JobCard.ts`, which stamps `changedAt`.
- **`Customer.vehicles` and `Vehicle.serviceHistory` are derived**, not
  stored — `toApi` emits them from the joined relation. The denormalisation
  bug class that needed `scripts/repairCustomerVehicles.ts` is gone with it.
- **Schema changes:** edit `config/schema.ts`, run `npx drizzle-kit generate
  --name <what-changed>`, commit the SQL in `drizzle/`. `config/db.ts` applies
  pending migrations at boot; the test harness applies them to PGlite. A
  migration that cannot apply fails the boot, loudly, instead of leaving a
  constraint silently unenforced the way a failed Mongo index build did.

## Postgres notes that will bite

- **Partial JSONB updates merge with `||`.** `garageUsecase` and
  `inventoryUsecase` do ``sql`${table.settings} || ${json}::jsonb` ``. The
  update zod schemas for those objects are written out without `.default()`
  on purpose: zod keeps a field's default when it is made optional, so a
  `.partial()` derived from the create schema fills every omitted key with
  its default and the merge then blanks the stored values.
  `tests/garageSettings.test.ts` caught exactly that.
- **Foreign keys refuse what Mongo tolerated.** `garage_id` cascades (a
  deleted garage takes its rows); `customer_id` / `vehicle_id` / `job_card_id`
  RESTRICT. Deleting a customer with vehicles, a vehicle with job cards, or a
  job card with an invoice returns **409** with a count in the message —
  `customerUsecase`, `vehicleUsecase`, `jobCardUsecase` check first so the
  user gets words rather than a constraint name. `errorHandler` maps a
  violation that slips through to 409 as a backstop.
  `tests/referentialIntegrity.test.ts` pins all of it.
- **Driver errors arrive wrapped.** Drizzle throws `DrizzleQueryError` with
  the `pg` error as `cause`; `utils/dbErrors.ts` unwraps it. `ON DELETE
  RESTRICT` raises SQLSTATE `23001`, not the `23503` that `NO ACTION` raises.
- **`db` is bound at boot, not buffered.** Mongoose queued queries until a
  connection appeared; `config/db.ts` throws if `connectDB()` (or the test
  harness's `setDb()`) has not run. `server.ts` awaits it before `listen()`.
- **Document numbers continue from the highest issued, under a lock.**
  `utils/numbering.ts` takes `SELECT ... FOR UPDATE` on the garage row inside
  the caller's transaction, then reads `max(NNNN)` — same `JC-YYMMDD-0001`
  format. Never go back to `count + 1`: once anything is deleted the count
  falls below the highest number and the next one collides. Mongo issued
  that duplicate silently (no unique index on invoices); Postgres refused it
  on the first invoice after cutover. It must be called inside
  `db.transaction()`. PGlite serialises transactions, so the lock is only
  genuinely exercised against Neon.
- **`double precision`, not `numeric`.** Mongoose stored JS doubles; `numeric`
  would come back as strings and change the tax parity both clients mirror.
- **Neon's free tier scales compute to zero after a few idle minutes.** The
  first request after a quiet spell pays a cold start of roughly a second.
  The app uses the pooled connection string with `Pool({ max: 5 })`.

## Owner verification

`usecases/verificationUsecase.ts` lets an **owner** (only — `authorize('owner')`
on the routes) confirm their email and phone by entering a six-digit code
from Settings on either client. Success stamps `users.emailVerifiedAt` /
`phoneVerifiedAt`, which every auth payload carries and the subscription
gate will read. Rules that are easy to break by tidying:

- **Codes are stored hashed** in `verification_challenges` with the address
  they were sent to; `updateUserProfile` clears `phoneVerifiedAt` when the
  number changes, and a code is refused if its target no longer matches.
- **Production refuses unconfigured delivery with 503.** `sendEmail` falls
  back to an Ethereal test inbox and `sendSms` merely logs when the provider
  is unset — either would leave an owner waiting for a code that never
  comes. Outside production the code is logged so the flow can be completed
  locally; that log line must never fire in production.
- Ten-minute expiry, five wrong attempts burn it, sixty-second resend
  cooldown, five codes per channel per hour — all in
  `models/VerificationChallenge.ts`. `tests/verification.test.ts` pins each.

## Locale and formatting

- PDFs use `formatMoney(amount, locale, { display: 'code' })` — PDFKit's
  built-in Helvetica has **no glyph for `₹`** or most currency symbols.
- Tax labels come from `locale.taxLabel` / `locale.taxIdLabel`, never `'GST'`.
- Tax-rate fallbacks are `?? 0`, never `?? 18` — an 18% default prints a
  fabricated tax line on a customer-facing invoice in a zero-tax country.
- Phone numbers go through `utils/phone.ts`, which returns `''` rather than
  guessing a country code. **An empty result means skip the send.**

## Reminder cron

Runs **every 30 minutes in UTC** and sends only during the hour that reads
09:00 in each garage's own timezone. `:00` and `:30` because several zones are
offset by a half hour (India +5:30) — an hourly-only schedule shifts Indian
garages to 09:30. Held reminders are left completely untouched, which is what
makes re-entry idempotent.

## Compatibility with the client repos

These values are duplicated in `garageCrm-fe` and `garageCrm-app`. Changing one
here without the others is a silent break:

- **Response envelope** — `{ success, data }`, and
  `{ success, count, total, pages, currentPage, data }` for lists.
- **Enum string values** in `types/domain.ts` — roles, job statuses, service
  types. Both clients mirror these in their `types/models.ts`.
- **The estimation tax formula** in `usecases/jobCardUsecase.ts` is the source
  of truth; both clients re-implement it as a live preview and must round to
  2dp identically. `tests/taxParity.test.ts` pins it.

## Verifying

```bash
npx tsc --noEmit && npm test
```

There is no lint script here. Tests run on `@electric-sql/pglite`, an
in-process Postgres that applies the same `drizzle/` migrations production
does; `tests/setup.ts` truncates every table after each test and mocks the
email and SMS services, so `smsService`'s own send path has no coverage —
cover logic in `utils/`, which is imported directly. `tests/helpers/dbAccess.ts`
has `findById` / `countRows` / `countInGarage` for the direct reads a test
occasionally needs around its API calls.

Before pushing dependency changes: `npx -y npm@10 ci --dry-run`.
